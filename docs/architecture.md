# Architecture

```
 PS3_GAME/ (the user's decrypted disc dump, never changed)
        |  r3_host unself             (C++, inside the host: decrypts USRDIR/EBOOT.BIN)
        v
 <data>/games/BCES01118-01.00/EBOOT.elf      and  <data>/disc/PS3_GAME/  (links to the dump + EBOOT.elf)
        |  ppu_loader / ppu_lifter / SPU lift       (Python, from the SDK)
        v
 <data>/games/<id>/recompiled/, spu/          C++ and C source of the game
        |  clang
        v
 <data>/games/<id>/module/game.dylib          the game, as a loadable library
        |  dlopen
        v
 host/r3_host --module game.dylib EBOOT.elf   the runtime: PPU/SPU support, HLE of the PS3 libraries, Metal, SDL
```

## Why a host and a module

Everything derived from the game must stay on the user's machine, and the prebuilt part must be the same for everyone.
So the program is split in two:

- **host** (`host/`, built by `scripts/build_host.sh`): the ps3recomp runtime, the toolkit's PPU boot scaffold and this
  port's sources (`main.cpp`, the HLE overrides in `r3_hle.cpp`, `spurs_lfqueue.cpp`, the input glue, `unself.cpp`).
  SDL2, glslang, SPIRV-Tools and SPIRV-Cross are linked in statically. It contains no game data and no LGPL code.
- **module** (`game.dylib`): the lifted PPU functions and SPU images and nothing else. Its undefined symbols are resolved
  against the host's exports when it is loaded (`-undefined dynamic_lookup`).

## The module ABI

- The host exports the whole runtime (`-force_load` + `-export_dynamic`).
- The host finds `function_table` and `function_table_count` in the module with `dlsym`. Its `ppu_recomp.h` is the lifter's
  own header preamble without the per-game table (`scripts/make_host_header.py`), so the two cannot drift apart.
- The module carries `r3_module_abi`, a hash over the headers and lifter it was built against (`sdk/ABI`). The host
  refuses a module with another value. The launcher's lift stamp and every compile cache key include it, so a new host
  rebuilds what depends on it.

## The SDK

`host/sdk/` next to the host holds the lifter tools, the headers the lift includes and `spu_dispatch_mt.c`, the one SPU
runtime source that has to be compiled with the lift (it relies on `musttail`, so it needs clang).
The launcher compiles the module against it.

## Executable decryption

`r3_host unself <EBOOT.BIN> -o <EBOOT.elf>` (`host/unself.cpp`, `host/crypto.cpp`) decrypts the retail disc's SELF
(program type APP): the metadata with the AES-256 key and IV of the SELF's key revision, then each section (AES-CTR,
zlib), and rebuilds the ELF. The key table `host/self_app_keys.inc` is generated by `tools/gen_app_keys.py` from RPCS3's
key vault at a pinned commit (SHA-256 checked) and committed, so neither building nor running needs the network. The
algorithm follows RPCS3's `unself.cpp`. `r3_host selftest` runs the crypto vectors, `test_r3_unself` a synthetic SELF.

## Launcher

`r3.py` and `launcher/r3_launcher/` (standard library only, Python 3.10+):

| Module | Does |
|---|---|
| `cli.py` | commands and options, the stages, `reset` / `clean-cache` |
| `game.py` | the data directory's layout (`Home`), reads `PARAM.SFO`, checks the PS3_GAME folder, decrypts the executable, links `disc/` |
| `profiles.py` | the supported versions: where the code ends, the extra SPU entries, the instruction patches (60 fps) |
| `lift.py` | runs the SDK's lifter and the SPU helper; the lift stamp (ELF, ABI, profile, helper) |
| `module.py` | compiles the translation units in parallel (cached per unit by source, command and ABI), links `game.dylib` |
| `toolchain.py` | finds Apple's clang (C++20, musttail) |
| `runner.py` | the host's environment and options, starts it in the data directory |
| `devhost.py` | in a checkout: rebuilds the host when its sources are newer |
| `doctor.py` | the checks of `r3.py doctor` |

`launcher/helpers/extract_spu_raw.py` finds the SPU code that is not an ELF (the SPURS policy modules, the job modules) in the
executable. Paths reach the host through the environment (`PS3_VFS_ROOT`, `PS3_PARAM_SFO`, `PS3_HDD0_ROOT`, `PS3_HDD1_ROOT` (the data directory: the game's cache is `/dev_hdd1/cache/<title id>`),
`PS3RECOMP_MSL_CACHE`, `R3_CONTROLS`) and the host's working directory is the data directory, so the host's own relative
defaults land there too.

## Data directory

`disc/PS3_GAME/` holds only links, so the 17 GB of the dump are not copied and the user's folder is not written to. The names
`gamedata/`, `cache/`, `controls.txt` and `logs/` are those the checkout always used: with `R3_HOME=<checkout>` (what `make`
sets) a developer's saves and caches carry over.

## Why there is no zig fallback

zig 0.17.0 was tried as a compiler for machines without the Xcode tools (2026-11-09). `zig c++` compiles all 263 units, but its
own Mach-O linker refuses to link the module: the lifted PPU code reads the host's thread-local `g_trampoline_fn` directly and
zig reports "illegal thread-local variable reference to regular symbol" for it with `-undefined dynamic_lookup`; it accepts neither
`-Wl,-U` nor `-flat_namespace`. An accessor call in front of each access would link, and would cost about 1% of the PPU threads
(module-abi/0001 had one until v0.19.0), so the launcher needs Apple's clang.
